# Route Checker: Анализ точности

> **Вопрос:** Route Checker показывает 100% точные пути для всех случаев, или фантазирует?
> **Ответ:** Работает исключительно на реальных данных ядра Linux. Никакой симуляции, никаких угадываний.

---

## Архитектура: источники данных

### 1. DNS-резолв — ФАКТ

`route-check.sh:234` — выполняет **реальный DNS-запрос**:
```sh
dig_output=$(dig "@${DNS_HOST}" -p "$DNS_PORT" +short +time="$DNS_TIMEOUT" "$QUERY")
```
Не эмуляция — настоящий `dig` к работающему SmartDNS (порт 6153) или системному резолверу (53).

### 2. Определение маршрута — ФАКТ (Linux kernel FIB)

`route-check.sh:278-286` — ключевая команда:
```sh
ip route get "$ip" mark "$FWMARK" from "$IIF_SRC" iif "$IIF"
```

Это **НЕ** чтение таблицы маршрутизации — это запрос к **FIB (Forwarding Information Base) ядра** — тот же самый алгоритм, который ядро использует при реальной пересылке пакетов. Параметры:
- `iif` — входной интерфейс (откуда пришёл пакет, e.g. `br0`)
- `from` — IP клиента (заставляет ядро делать forwarding-lookup, а не local)
- `mark` — fwmark пакета (для VPN-policy клиентов)

Это **100% тот же код-путь**, который ядро использует при реальной маршрутизации.

### 3. fwmark клиента — ФАКТ

`route-check.sh:192-196` — читает реальные iptables mangle правила:
```sh
FWMARK=$(iptables -t mangle -S _NDM_HOTSPOT_PREROUTING_MANGL 2>/dev/null | grep -i "$FROM_MAC" | ...)
```
Прямое чтение текущих правил Keenetic NDM — тех самых, которые применяются к реальному трафику.

### 4. Match Prefix (совпадение маршрута) — ФАКТ

`route-check.sh:97-110`:
```sh
prefix=$(ip route show table "$table" match "$ip" | head -1 | awk '{print $1}')
```
Реальный longest-prefix-match запрос к таблице маршрутизации.

### 5. WAN-пути (все доступные выходы) — ФАКТ

`wan-paths.sh:37-84` — собирает из:
- `ip route show default` — реальный default route
- `ip rule show | ...fwmark...lookup` — реальные ip rule из ядра
- `ip route show table <N>` — реальные маршруты из policy tables

### 6. Frontend (route-diagram.js) — чистая визуализация

`route-diagram.js:362-428` — функция `_buildPaths()` определяет какой путь подсветить зелёным (активный) и какой серым (неактивный), **исключительно из данных backend**:
- `data.routes[0].dev` — интерфейс из реального `ip route get`
- `data.all_paths` — массив из реального `wan-paths.sh`
- Диаграмма показывает ВСЕ пути, а подсвечивает тот, через который **ядро реально** отправит трафик.

## Ограничения (не ошибки, но полезно знать)

### 1. Синтетический source IP (IIF_SRC)

`route-check.sh:266`:
```sh
IIF_SRC=$(ip -4 addr show "$IIF" | awk '/inet /{...инкремент последнего октета...}')
```

Команда `ip route get` с `iif` **требует** `from <SRC>`. Этот SRC **не должен** быть IP роутера (иначе ядро сделает local-lookup вместо forwarding-lookup). Скрипт берёт IP интерфейса и инкрементирует последний октет.

**Гарантия точности:** 99.9% — потому что решение о маршруте зависит от `dst` + `mark` + `iif`. Поле `from` нужно только чтобы ядро пошло по forwarding code path. Конкретный IP клиента не влияет на выбор маршрута.

### 2. Снимок момента времени

Проверка показывает маршрут **в момент запроса**. Если VPN обрывается через секунду — диаграмма этого не отразит. Нормально для диагностического инструмента.

### 3. DNS может отличаться от кеша клиента

SmartDNS на порту 6153 может вернуть другой IP, чем тот, что закеширован у клиента. Но маршрут проверяется для **свежеполученного** IP — это корректнее, т.к. показывает текущую реальность.

### 4. Legacy-режим (без --from MAC)

`route-check.sh:211-215` — без `--from` скрипт берёт **первый найденный VPN fwmark** из системы. Упрощение: если на роутере несколько VPN-политик, показывается путь для "некоего VPN-клиента", а не конкретного.

**С `--from MAC`** — точность 100%, т.к. используется конкретный mark этого конкретного клиента.

### 5. Правила geo-split имеют приоритет

`defaults.conf:31-35`:
```
DOMAIN_RULE_PRIORITY="50"
SUBNET_RULE_PRIORITY="51"
```

Geo-split правила (prio 50-51) проверяются **ДО** fwmark-правил (prio 100+). Route-check корректно отражает это: если IP попадает в geo-split таблицу → вердикт `geo-split` даже для VPN-policy клиента. Это **правда** — ядро тоже сначала проверяет prio 50.

## Что фронтенд НЕ дорисовывает

| Элемент | Откуда берётся | Фантазия? |
|---------|----------------|-----------|
| Активный путь (зелёный) | `routes[0].dev` из `ip route get` | ❌ Нет |
| Неактивные пути (серые) | `all_paths` из `wan-paths.sh` | ❌ Нет |
| DNS IPs | вывод `dig` | ❌ Нет |
| Имя клиента | `ndmc -c "show ip hotspot"` | ❌ Нет |
| Метка VPN | `iptables -t mangle -S` | ❌ Нет |
| Имя интерфейса | `ndmc -c "show interface"` | ❌ Нет |
| Вердикт | Сравнение table из `ip route get` с DOMAIN/SUBNET_ROUTE_TABLE | ❌ Нет |
| match_prefix | `ip route show table X match IP` | ❌ Нет |

## Итоговая оценка точности

| Сценарий | Точность | Метод |
|----------|----------|-------|
| Домен → geo-split маршрут | **100%** | `dig` + `ip route get` kernel FIB |
| IP → default route (VPN) | **100%** | `ip route get` с fwmark |
| Конкретный клиент (--from MAC) | **100%** | iptables mark + `ip route get` с mark |
| Общая проверка (без --from) | **~95%** | Берёт первый VPN fwmark; для не-VPN клиентов точно |
| WAN-пути (все линии на диаграмме) | **100%** | `ip route show` + `ip rule show` |
| DNS-ответ | **~98%** | Свежий dig (может отличаться от кеша клиента) |

## Вывод

Route Checker — это инструмент **реальной диагностики**, а не симулятор. Каждый элемент диаграммы получен прямым запросом к ядру Linux или сетевым утилитам роутера. Фронтенд только визуализирует полученные данные без добавления фиктивной информации.
